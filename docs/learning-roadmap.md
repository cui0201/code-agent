# 学习路线：跟着 code-agent 学 AI 应用工程

> 这份路线把 code-agent 这个项目当作教材。它不是"AI 知识大全"，
> 而是"这个项目里用到的每一个概念，应该怎么学、看哪段代码、做什么实验、怎么自测"。
>
> 配套文档：[项目方案](code-agent-plan.md)（做什么）、[开发设计文档](design/dev-design.md)（怎么做，
> 含每个阶段的实测数据）、[README](../README.md)（怎么跑）。

---

## 0. 怎么用这份路线

三种用法，按你的目标挑一种：

| 用法 | 做法 | 适合 |
| --- | --- | --- |
| **按阶段跟做** | 从阶段一读到阶段四，每个知识点都动手跑一遍实验 | 从零开始学，时间充裕 |
| **按主题补课** | 直接跳到你不熟的主题（例如只补 RRF、只看拒答） | 已有 RAG 基础，想补短板 |
| **面试前复习** | 只看每节的「自测」与第 8 节问答清单，答不上来再回看代码 | 准备面试 |

每个知识点的固定结构：

```
【要理解什么】概念层面的核心，不是 API 用法
【看哪段代码】项目里的具体文件与类
【动手实验】改了它，观察什么变化
【自测】能答上来才算学会
```

**前置要求**：Java 基础、Maven、会写 Spring Boot 的 `@RestController`。
**不需要**：微积分、Python、深度学习框架使用经验。

## 1. 知识地图

这个项目涉及的知识分四层，**越往下越通用、越值得先学**：

```
第四层  智能体与工程化     工具调用、MCP、缓存、增量索引、可观测
        ─────────────────────────────────────────────
第三层  评估与迭代         评测集设计、指标、用数据做决策
        ─────────────────────────────────────────────
第二层  生成与可信         提示组装、引用校验、拒答、重排、文档漂移
        ─────────────────────────────────────────────
第一层  检索基础           嵌入、相似度、切块、BM25、混合检索、RRF
```

**学习顺序建议按层来，而不是按代码模块来**。原因：上层的一切优化都以"检索能不能找到对的证据"为前提。
这个项目里有现成的反例——P3 花了力气做重排，结果实测重排既不提升质量又把延迟拉到 4 秒，
根本原因是底层的召回与判据还不牢（见设计文档 14.7）。

## 阶段一：检索基础（对应 P0–P2）

### 1.1 嵌入与向量相似度

**【要理解什么】**

- 嵌入就是把文本映射成一个定长向量，语义相近的文本向量方向相近；
- 余弦相似度衡量的是"方向夹角"，与向量长度无关；
- **归一化之后，余弦相似度等价于点积**——这不是数学技巧，而是工程优化：
  省掉每对向量的两次开方与一次除法。

**【看哪段代码】**

- `code-agent-core/src/main/java/com/example/codeagent/core/math/VectorMath.java`
  —— 手写的余弦相似度与归一化。**刻意不用框架**，因为这两行公式是理解向量检索的地基。
- `code-agent-indexer/.../embed/LocalOnnxEmbeddingClient.java`
  —— 本地 ONNX 模型，输出向量已归一化，并带一层内容哈希缓存。

**【动手实验】**

1. 打开 `VectorMathTest`，把 `normalized()` 里的 `scale` 改成 `1.0 / norm`（少一次开方），
   看哪些测试失败——理解"归一化到底改了什么"。
2. 用 `LocalOnnxEmbeddingClient` 嵌三句话：一句问句、一句相关、一句无关，打印两两余弦值。
   你会看到相关与无关的差距往往只有 0.1 左右（本项目实测：相关 0.69，无关 0.49）。
3. 把 `EmbeddingCache` 的容量改成 1，重新索引，观察耗时与命中率变化。

**【自测】**

- 为什么余弦相似度要做归一化？归一化后能用点积代替吗？
- 为什么"相关与无关的相似度差距很小"这件事，会直接威胁到"用阈值判断有没有依据"？

### 1.2 切块策略

**【要理解什么】**

- 切块决定了检索的**最小语义单元**，也决定了引用能不能精确落地；
- 定长切块会切断方法、切断文档章节；结构化切块（AST、Markdown 标题）不会；
- 切块 id 必须**稳定**（不含行号），否则代码一改，历史引用全部失效。

**【看哪段代码】**

- `code-agent-indexer/.../chunk/LineWindowChunker.java` —— 反面对照组，刻意保留。
- `code-agent-indexer/.../chunk/JavaAstChunker.java` —— 类/方法级切块，
  注意 `classSummaryChunk`（合成摘要）与 `methodChunk`（源码逐字片段）的区别。
- `code-agent-indexer/.../doc/MarkdownDocChunker.java` —— 按标题切章节，生成锚点。
- `code-agent-indexer/.../chunk/CompositeChunker.java` —— 按扩展名分发。

**【动手实验】**

1. 跑 `mvn -pl code-agent-eval -am verify -Dit.test=RagEvaluationIT -Dfailsafe.failIfNoSpecifiedTests=false`，
   看 `code-agent-eval/target/rag-report.md` 里 ast 与 line-window 的对比。
   本项目实测：召回 **75% vs 41.7%**，命中块平均多余行数 **0 vs 9.5**。
2. 把 `code-agent.chunk.window-lines` 从 60 改成 20，重新跑评测——观察"多余行数"会不会下降、
   召回会不会反而变差。
3. 在 `examples/demo-project` 里新建一个超过 100 行的类，看两种切块策略分别切成几块。

**【自测】**

- 为什么切块 id 不能包含行号？
- 类块为什么用"合成摘要"而不是整个类的源码？
- "命中块平均多余行数"这个指标衡量的是什么？它影响的不只是可读性，还影响什么？

### 1.3 稀疏检索与 BM25

**【要理解什么】**

- BM25 的两个核心机制：**词频饱和**（一个词出现 10 次不代表比出现 5 次重要一倍）
  与**长度归一化**（长文档天然容易命中更多词）；
- IDF 让"稀有词"获得高权重，这正是代码检索里**标识符**的价值来源；
- 分词对代码场景至关重要：`createOrder` 既要保留整体 `createorder`，
  也要拆成 `create` 与 `order`。

**【看哪段代码】**

- `code-agent-retrieval/.../keyword/Bm25Index.java` —— 手写倒排索引与打分公式。
- `code-agent-retrieval/.../keyword/Tokenizer.java` —— 标识符切分 + 中文二元组。
- `code-agent-retrieval/.../query/IdentifierExtractor.java` —— 识别"用户点名了符号"。

**【动手实验】**

1. 把 `Tokenizer` 里"整体小写形式"那一路去掉（只保留驼峰拆分），重新跑评测。
   你会看到标识符查询（如 `createOrder`）的召回明显下降——这就是"为什么两种形式都要保留"的答案。
2. 把 BM25 的 `k1` 从 1.2 改成 0（彻底取消词频饱和），观察排序变化。
3. 用 `Bm25IndexTest` 里的三个切块做实验：问"createOrder"和问"订单"分别命中谁。

**【自测】**

- BM25 的 `k1` 与 `b` 分别控制什么？把 `b` 设成 0 会发生什么？
- 为什么中文要用二元组切分？有没有更好的做法，代价是什么？

### 1.4 混合检索与 RRF

**【要理解什么】**

- 稠密检索擅长语义，稀疏检索擅长精确匹配，两者**互补而非替代**；
- RRF 只用**排名**不用分数，因此天然免疫两路分数的量纲差异
  （余弦落在 0~1，BM25 是无上界的对数分数）；
- RRF 的固有缺陷：它奖励"两路都靠前"，
  会**埋没"只被一路强烈命中"的结果**——本项目实测踩到过（见设计文档 14.8）。

**【看哪段代码】**

- `code-agent-retrieval/.../fusion/RrfFuser.java` —— 手写融合，注意归一化那一步。
- `code-agent-retrieval/.../HybridRetriever.java` —— 两路召回 + 拒答判据，
  类注释里记录了"为什么不能用 BM25 分数做拒答阈值"的完整教训。

**【动手实验】**

1. 把 `RrfFuser.DEFAULT_K` 从 60 改成 1，观察排序如何被"单路第一"主导。
2. 把两路权重从 `[1.0, 1.0]` 改成 `[1.0, 2.0]`（偏向关键词），重跑评测，
   看 q012 那类"被关键词路排第一"的用例是否被救回。
3. 关掉关键词路（`code-agent.retrieval.strategy=vector`），重跑评测，
   观察召回从 91.7% 掉到 75% 的具体是哪些题。

**【自测】**

- 为什么 RRF 用排名而不用分数？什么情况下这个选择会变成缺点？
- 本项目里"问 OrderController 暴露了哪些接口，结果命中了 OrderEventPublisher"——
  这个错误为什么纯向量检索解决不了？

## 阶段二：生成与可信（对应 P3–P4）

### 2.1 交叉编码器与重排

**【要理解什么】**

- 双编码器把查询与文档**分别**编码，快但粗；交叉编码器把两者**拼在一起**过模型，准但慢；
- 因此重排只能用在少量候选上，这是"先召回后精排"架构的根本原因；
- **重排不是免费的提升**：本项目实测它在中文问句 + Java 代码场景下没有收益，
  且延迟达 4145 ms/查询。

**【看哪段代码】**

- `code-agent-core/.../port/Reranker.java` —— 端口定义与实现约定。
- `code-agent-retrieval/.../rerank/OnnxCrossEncoderReranker.java` —— JVM 内 ONNX 推理。
- `code-agent-retrieval/.../RerankingRetriever.java` —— 装饰器模式，注意拒答逻辑留在被装饰方。

**【动手实验】**

1. 下载模型（`scripts/download-reranker-model.sh`），用
   `-Dcodeagent.rerank.eval=true` 跑重排对比，亲眼看 MRR 是升还是降。
2. 把 `MAX_DOCUMENT_CHARS` 从 2000 改成 200，观察结果变化——
   理解"交叉编码器的输入长度限制"为什么需要主动裁剪。
3. 换一个代码感知的重排模型，看结论是否翻转（这是文档里给出的重新评估条件之一）。

**【自测】**

- 为什么交叉编码器不能直接用来做全量检索？
- 如果一个优化"看起来是标准做法"但实测没用，你会怎么决策？依据是什么？

### 2.2 提示组装与上下文预算

**【要理解什么】**

- 上下文不是越多越好：塞入低相关片段会增加延迟与幻觉；
- **编号即引用**：给证据编号，编号与证据列表下标一一对应，答案里的 `[n]` 才能被程序校验；
- 展示顺序与编号顺序必须一致，否则引用会指向错误的片段。

**【看哪段代码】**

- `code-agent-agent/.../PromptBuilder.java` —— 预算裁剪、代码与文档分区、编号分配。
- `code-agent-web/.../service/IndexingFacade.java` —— 三套索引必须同源的理由。

**【动手实验】**

1. 把 `code-agent.retrieval.max-evidence-chars` 从 12000 改到 2000，
   观察 `Prompt.usedChunks()` 与最终答案质量的变化。
2. 在 `render()` 里把代码块与文档块的顺序对调，看引用是否错位——
   这是理解"展示顺序即编号顺序"最快的办法。

**【自测】**

- 为什么 `Prompt.evidence` 必须按展示顺序返回，而不能按检索顺序返回？
- 上下文预算应该优先给代码还是文档？依据是什么？

### 2.3 引用校验与拒答

**【要理解什么】**

- 幻觉不能靠提示词根治（模型会编造 `[7]`，哪怕只给了 3 个片段），
  只能在**输出端用程序校验**；
- 拒答是延迟与成本优化：无依据时不调用大模型，既不会编造，又省一次请求；
- 绝对阈值判据在中文语料上很脆弱——**中文问句对任意中文技术文本的余弦基线就有 0.6 左右**。

**【看哪段代码】**

- `code-agent-agent/.../CitationValidator.java` —— 白名单校验，越界编号识别。
- `code-agent-agent/.../RefusalPolicy.java` —— 拒答判据。
- `code-agent-agent/.../QaService.java` —— 主编排，含引用失败后的**带反馈重试**。

**【动手实验】**

1. 把 `RefusalPolicy` 的阈值调到 0.9，重跑评测，观察"误拒"（该答的题被拒）出现在哪些用例上。
2. 把 `code-agent.guard.citation-retry` 从 1 改成 0，用 `QaServiceTest` 观察重试路径的差异。
3. 在 `CitationValidator` 的正则里加一条规则，识别形如 `[1,2]` 的合并引用，补上测试。

**【自测】**

- 为什么引用校验必须由程序做，而不能写进提示词？
- 拒答阈值是怎么定的？为什么说它已经"接近失效"？
- 引用校验失败后为什么要"带反馈重试"而不是直接重试？

### 2.4 文档通道与漂移检测

**【要理解什么】**

- 文档是**第二信源**：它能回答代码里读不出来的"为什么"，但会过期；
- 过期的文档比没有文档更危险——它给出看起来权威、实际错误的答案；
- 漂移检测的两条判据都不需要保存历史状态：引用符号已不存在、被引用代码比文档新。

**【看哪段代码】**

- `code-agent-indexer/.../doc/MarkdownDocChunker.java` —— 标题切块、锚点生成、同名锚点去重。
- `code-agent-indexer/.../doc/DocSymbolExtractor.java` —— 从反引号里抽符号，以及**哪些不该被抽**。
- `code-agent-indexer/.../doc/DocumentDriftDetector.java` —— 两条判据与"字段引用降级到类型"的容错。

**【动手实验】**

1. `touch examples/demo-project/src/main/java/com/acme/order/OrderService.java`，
   重新索引，观察哪些文档块被标记为过期。
2. 在 `docs/api/order-api.md` 里加一句引用不存在的符号（例如 `` `OrderService#cancelOrder` ``），
   重新索引，观察"符号已不存在"这条判据生效。
3. 删掉 `DocSymbolExtractor.normalize()` 里"含空白/斜杠/逗号则拒绝"的判断，
   重新索引，看误报如何出现——理解"抽取规则过宽"的代价。

**【自测】**

- 漂移检测为什么不需要记录历史版本？
- 文档块为什么用锚点而不是行号做引用？
- `OrderRequest#requestId` 这种"字段引用"为什么要降级到类型再判断？

## 阶段三：结构化与工程化（对应 P5–P6）

### 3.1 符号图与影响面分析

**【要理解什么】**

- 有些问题向量检索**永远答不了**："改动这个方法会影响哪些对外接口"——
  答案不在任何一段代码的语义里，而在代码之间的结构关系里；
- 语法树 ≠ 类型解析：JavaParser 能切块但答不出"这个调用指向哪个方法"，Spoon 可以；
- 图的价值在于**关系类型**：继承、实现、调用、声明，混在一起就没法给出精确结论。

**【看哪段代码】**

- `code-agent-indexer/.../graph/SpoonGraphBuilder.java` —— Spoon 建图，含 `noClasspath` 的取舍。
- `code-agent-indexer/.../graph/SymbolKeys.java` —— **两套工具产出同一把钥匙**的归一化规则。
- `code-agent-indexer/.../graph/SymbolGraph.java` —— JGraphT 存储与广度优先遍历。
- `code-agent-indexer/.../graph/ImpactAnalyzer.java` —— 输入解析（支持简写）与三类影响的汇总。

**【动手实验】**

1. 启动服务，索引样例工程，然后：

   ```bash
   curl -s "localhost:8080/v1/impact?symbol=OrderService%23createOrder&depth=2" | jq
   ```

   观察结论：调用方是 `OrderController#create`，受影响文件是 `OrderController.java`。
   人工核对源码，验证这条结论是否正确。
2. 把 `depth` 从 1 改到 3，观察传播范围如何扩大。
3. 把 `SpoonGraphBuilder` 里的 `setNoClasspath(true)` 改成 `false`，
   用本项目自身（含 Spring AI 依赖）做索引对象，观察会发生什么——理解"完整类型解析"的代价。

**【自测】**

- 为什么符号键需要归一化？不归一化会出现什么具体故障？
- 为什么 `noClasspath` 模式下要"宁可少几条边，也不要错几条边"？
- 影响面分析的结果里，为什么"受影响文件列表"比"图长什么样"更重要？

### 3.2 缓存、增量索引与可观测

**【要理解什么】**

- **缓存的价值来自"跳过工作"，不是"存东西"**：命中一次就省掉检索与大模型调用，
  所以收益最大的一步优化往往是最简单的缓存；
- **缓存失效比缓存命中更危险**：答案里的引用绑定在具体版本的代码上，
  代码一变，缓存里的引用就可能指向错误位置，因此宁可整体清空也不做精细失效；
- **增量索引的复用单位是文件而不是代码块**：改一个方法会让它之后的所有块行号位移，
  按块复用会出现"id 还对得上、行号全错"；
- **必须看分位数而不是平均值**：一次 5 秒的慢请求在 100 次平均里只体现为多 50 ms，
  但用户体验是"偶尔卡得没法用"。

**【看哪段代码】**

- `code-agent-agent/.../SemanticCache.java` —— 两级缓存（精确层 + 语义层）与失效策略。
- `code-agent-indexer/.../IncrementalIndexCache.java` —— 按文件复用切块与向量。
- `code-agent-indexer/.../IndexingService.java` —— 增量后的流水线，
  注意"漂移检测每次都要跑、符号图只在 Java 变化时重建"这两处不对称。
- `code-agent-indexer/.../embed/EmbeddingCache.java` —— 更细一层的内容哈希缓存。
- `code-agent-web/.../service/AgentMetrics.java` —— 分位数怎么算、为什么要保留样本。
- `code-agent-web/.../service/IndexingFacade.java` —— 索引重建后缓存失效的触发点。

**【动手实验】**

1. 启动服务后连续两次 `POST /v1/index`，比较响应里的 `reusedFiles` 与 `elapsedMs`。
   本项目实测：**872 ms（43 块全嵌入）→ 4 ms（0 块嵌入）**。
2. 只改一个 Java 文件再索引，观察 `embeddedChunks` 是否只包含该文件的块；
   然后只改一个 Markdown 文件，观察符号图是否被复用（日志里会有"复用已有符号图"）。
3. 同一个问题问两次，看 `GET /v1/metrics` 里的 `cacheHits` 与 `cacheHitRatio` 变化，
   并注意第二次的 `retrievalMs` 为 0——缓存命中时连检索都不做。
4. 把 `code-agent.cache.semantic-threshold` 从 0.95 调低到 0.8，
   换几种说法问同一件事，观察语义层命中；再调回 0.95 看差异。
5. 用 `curl -N "localhost:8080/v1/ask/stream?question=..."` 观察 SSE 事件顺序，
   注意 `citations` 一定在全部 `delta` 之后。

**【自测】**

- 为什么拒答结果不进缓存？缓存它会导致什么用户体验问题？
- 增量索引为什么以文件而不是代码块为复用单位？
- 为什么"漂移检测每次都要跑"而"符号图可以不重建"？两者的差别在哪？
- 流式模式下为什么不做引用重试？如果一定要支持，你会怎么设计？
- 什么情况下平均值会掩盖问题？举一个你项目里可能出现的例子。

## 阶段四：评估驱动（对应 P7）

### 4.1 评测集与指标

> 本项目已经把这一节的内容落地了：44 条用例分布在两个语料上，
> 报告带分类指标与语料指纹。**分类指标比总分重要得多**——
> 实测结果表明，只看总分会得到"系统还行"的印象，
> 分开看才发现"单点实现问题 100%、跨文件综合与拒答只有 33%"。

**【要理解什么】**

- 没有评测集，"优化"就是玄学；
- 指标要能反映**你真正在意的东西**：召回率告诉你"找没找到"，
  MRR 告诉你"排得准不准"，拒答准确率告诉你"会不会编造"；
- 拒答题必须进评测集——只测"能不能答对"的系统，会奖励一个永远不拒答的实现。

**【看哪段代码】**

- `code-agent-eval/src/test/resources/golden/demo-project.yml` —— 14 条用例的定义方式。
- `code-agent-eval/.../RagEvaluator.java` —— 指标计算，注意 `rank` 与 `extraLines`。
- `code-agent-eval/.../EvaluationReport.java` —— 报告渲染。
- `code-agent-eval/.../RagEvaluationIT.java` —— 同一批问题跑多套策略做横向对比。

**【动手实验】**

1. 自己加 3 条用例（一条证据题、一条拒答题、一条文档题），跑评测看是否被正确判定。
2. 把 `topK` 从 8 改成 3，观察召回率下降多少——这就是"上下文预算"的量化代价。
3. 故意把 `MIN_SCORE` 调到 0.5，观察拒答准确率与召回率如何此消彼长。

**【自测】**

- Recall@k 与 MRR 分别衡量什么？为什么本项目两个都要看？
- 如果只测"能不能答对"，会诱导出什么样的实现？

### 4.2 用数据做决策（本项目的三个真实案例）

这一节是本项目最值得学的部分：**同样的数据，如何推翻你原本以为正确的决定**。

| 决策点 | 原本的预期 | 实测结果 | 最终决策 |
| --- | --- | --- | --- |
| P1 切块策略 | AST 切块应该大幅提升召回 | 召回 75% vs 62.5%，但**引用多余行数 0 vs 12.6** | 采用 AST，并把"引用精度"列为第一收益 |
| P3 重排 | 交叉编码器精排是标准做法，应该有效 | MRR 0.9167 → 0.8750，延迟 4145 ms/查询 | **不默认启用**，保留实现与对比能力 |
| P4 拒答阈值 | 调大阈值就能过滤无关问题 | 拒答类最高分 0.603、证据类最低分 0.626，只差 0.023 | 记录为"阈值法接近失效"，交给机制层面的改进 |

**【要理解什么】**

- **"业界标准做法"不是论据，实测数据才是**；
- 一个优化只要有一条硬性代价（例如延迟超预算 1.6 倍），就足以否决它；
- 当调参的余地窄到 0.023，说明方向错了，该换机制而不是继续调数字。

**【自测】**

- 如果评测结果是"没提升"，你会怎么处理这个优化？删掉、保留、还是默认关闭？
- 怎么判断"再调一次参就能好"和"这个方向本身有问题"？
