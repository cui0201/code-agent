# 项目定位与价值

> 这份文档回答一个必须回答的问题：**已经有 Codex、Claude 这类能直接读仓库的智能体了，
> 为什么还需要 code-agent？**
>
> 答案不是"我们做得更好"，而是"解决的不是同一个问题"。

---

## 1. 先承认：通用编码智能体更强的地方

把仓库交给 Codex / Claude，它们在**一次性深度问题**上确实更强：

- 能连续读几十个文件、自己决定下一步看哪里；
- 能跟踪跨模块的引用链；
- 能给出重构建议、直接改代码。

本项目的评测也证实了这一点：跨文件综合类问题的通过率只有 **63.6%**，
远低于单点实现解释的 **100%**。如果你的需求只是"偶尔问一句这个项目怎么工作"，
把仓库丢给通用智能体更省事。

**因此 code-agent 的定位不是"更好的 Codex"，而是团队内部的代码知识服务。**

---

## 2. 五个决定性差异

### 2.1 单次成本：整个仓库 vs 6~10k token

通用智能体回答每个问题都要重新读取文件、执行多轮工具调用。
一个中等规模仓库，一次较深的问题通常要消耗几万到几十万 token。

code-agent 在提问前就已经建好索引，每次只把**检索命中的 5~8 个片段**
（约 6k~10k token）交给模型：

| | 通用编码智能体 | code-agent |
| --- | --- | --- |
| 每次读什么 | 按需读大量文件 | 固定 5~8 个片段 |
| 典型输入 token | 数万 ~ 数十万 | 6k ~ 10k |
| 多轮工具调用 | 每次都要重新探索 | 一次检索，无工具循环 |

提问越频繁，差距越大。同一个"下单接口怎么校验金额"被团队问十次，
通用智能体要读十遍仓库；code-agent 第二次可能直接命中语义缓存。

### 2.2 延迟：索引一次，回答按秒算

实测（本机、本地 ONNX 嵌入、deepseek-flash）：

| 阶段 | 耗时 |
| --- | --- |
| 检索（向量 + BM25 + RRF） | 约 2 ms |
| 相关性判官 | 1~2 s |
| 答案生成 | 2~7 s（取决于模型与输出长度） |
| 语义缓存命中 | 跳过检索与生成 |

而通用智能体每次都要先"探索仓库"，首字延迟通常以十秒计。

### 2.3 数据边界：全量外发 vs 片段外发

把仓库分享给外部智能体，意味着**整个代码库**要离开你的机器。
很多公司不允许这样做。

code-agent 的设计是：**全量代码留在本地，只把检索命中的片段发给 LLM**。
这不是"优化项"，而是能否在真实企业环境里使用的前提条件。

配套约束也写在实现里：

- 源码以只读方式挂载，应用不会修改被索引的工程；
- 索引快照含代码原文，按源码同等敏感级别管理，且默认被 `.gitignore` 排除；
- 发送给外部模型的内容只有问题 + 命中片段，不是整个仓库。

### 2.4 引用：程序校验 vs 尽力而为

通用智能体的引用是"尽力而为"：可能指向大致位置，也可能编造一个不存在的行号。

code-agent 把引用做成了**机制**：

1. 每条证据带 `路径:起始行-结束行` 或 `文档路径#锚点`；
2. 模型必须用 `[n]` 标注结论，`n` 只能来自本次注入的片段；
3. 程序解析答案里的所有 `[n]`，逐一比对白名单；
4. 越界引用会触发一次带反馈的重试，仍失败则降级并标注"引用校验未通过"。

**引用可点开、可核对、可审计**——这是"能用来回答同事问题"和"只能自己看看"的分界线。

### 2.5 可重复性：每次不同 vs 可回归

通用智能体的回答每次都不一样，无法做回归测试，也无法回答"改了检索参数到底变好还是变差"。

code-agent 有：

- **106 条 golden 评测用例**，覆盖事实查询、实现解释、设计决策、文档、跨文件、拒答；
- 每次 `mvn verify` 自动跑两套语料并输出报告；
- 报告带**语料指纹**（所有文件路径 + 内容哈希的摘要），指纹相同则结果可复现；
- 分类指标，能看出"系统在哪类问题上弱"，而不是只有一个总分。

这一点直接决定了项目可以持续演进：本项目里三次"实测推翻了原本的预期"
（AST 切块的主要收益是引用精度而非召回、cross-encoder 重排默认关闭、
绝对阈值拒答失效），都是靠这套评测发现的。

### 2.6 接入形态：人机对话 vs 系统能力

通用智能体是给人用的对话界面；code-agent 是**可以被系统调用**的能力：

| 接口 | 用途 |
| --- | --- |
| CLI | `--index` / `--ask`，脚本化 |
| REST + SSE | 内部 Wiki、问答机器人、前端流式展示 |
| MCP Server | 直接挂给 IDE / 编码助手作为工具 |
| `/v1/impact` | 结构化影响面分析 |

### 2.7 结构化查询：符号图 vs 阅读理解

"改动 `OrderService.createOrder` 会影响哪些对外接口"——这个问题的答案不在任何一段代码的语义里，
而在代码之间的调用关系里。

code-agent 用 Spoon 建符号图（继承 / 实现 / 调用 / 声明），答案是确定的：
`OrderController#create`，1 跳，受影响文件 `OrderController.java`。
通用智能体也能推出来，但要靠读代码推理，慢且可能漏。

## 3. 什么时候该用它

| 场景 | 为什么适合 |
| --- | --- |
| 团队高频问同一批项目问题 | 缓存 + 固定上下文，边际成本极低 |
| 代码不能出内网 | 只外发命中片段 |
| 回答需要被审计 | 引用强制可校验 |
| 要把问答嵌进内部工具 | REST / SSE / MCP |
| 需要"改了这里影响什么" | 符号图给出确定答案 |
| 想持续改进问答质量 | 106 条评测集 + 分类指标 |

## 4. 什么时候不该用它

| 场景 | 建议 |
| --- | --- |
| 一次性架构深潜、跨模块综合 | 用 Codex / Claude 直接读仓库 |
| 重构建议、直接改代码 | 用通用编码智能体 |
| 项目很小（几个文件） | 直接读更快，索引不划算 |
| 需要多轮追问、探索式分析 | 通用智能体更合适 |
| 需要最新代码的即时答案 | 先重建索引；否则可能答旧内容 |

---

## 5. 与通用智能体不是竞争，而是互补

code-agent 提供 MCP Server，可以直接挂给支持 MCP 的客户端（IDE、编码助手）：

- 通用智能体需要**精确定位**时，调用 `search_code`；
- 需要**影响面**时，调用 `impact_analysis`；
- 需要**单个符号源码**时，调用 `get_symbol`。

也就是说，它相当于给通用智能体装了一个"精确、便宜、可审计的项目记忆"。

---

## 6. 诚实的短板

写进文档而不是藏起来，因为知道边界比夸大能力更重要：

| 短板 | 现状 |
| --- | --- |
| 跨文件综合 | 63.6%（评测集） |
| 纯检索闸门下的拒答 | 66.7%；生产用 LLM 判官后实测 12/12 |
| 评测集规模 | 106 条，样本仍偏小 |
| 单机单工程 | 一个实例只索引一个目录 |
| 无认证 | 默认只应监听内网 |
| 重排 | 实测无收益且延迟高，默认关闭 |

---

## 7. 怎样衡量它是否成功

| 指标 | 目标 | 当前实测 |
| --- | --- | --- |
| 证据召回率（混合检索，无闸门） | > 90% | **96.9%** |
| 端到端拒答准确率（含判官） | > 90% | **12/12** |
| 引用准确率 | > 95% | 由引用白名单校验保证 |
| 单问上下文 | < 10k token | 6~10k |
| 重启索引 | < 1 s | **228 ms** |
| 冷启动索引（1280 块） | — | 10.8 s |

## 8. 简历与面试表述

**一句话**

> 面向 Java 工程的本地代码知识服务：一次索引、按需检索，把每次提问的上下文从整个仓库
> 压缩到 6~10k token，并用符号图与引用校验保证答案可定位、可复现、可审计。

**三句话展开**

1. 用 JavaParser 做 AST 结构化切块、Spoon 建符号图，把源码、文档、配置与生成文档
   统一成可检索的证据；
2. 稠密向量 + BM25 混合召回 + RRF 融合，配合 LLM 相关性判官与引用白名单校验，
   在 106 条评测集上达到 96.9% 召回与 12/12 拒答；
3. 提供 REST / SSE / MCP 三种接入方式，除大模型 API 外全链路本地部署，
   索引快照使重启后重建从 14 秒降到 228 毫秒。

**一定会被追问的问题**

| 追问 | 回答要点 |
| --- | --- |
| 为什么不直接用 Cursor / Codex？ | 见第 2 节：成本、数据边界、引用可审计、系统集成 |
| 怎么保证不胡说？ | 引用白名单 + 拒答判官 + 无依据不调用模型 |
| 怎么证明有效？ | 106 条评测集、分类指标、语料指纹、可复现 |
| 你踩过什么坑？ | RRF 埋没单路第一、中文文档让阈值失效、Javadoc 导航页污染语料（详见设计文档 14.x） |

---

## 9. 一页总结

| 问题 | 通用编码智能体 | code-agent |
| --- | --- | --- |
| 一次深度探索 | **更强** | 较弱 |
| 高频重复问答 | 每次重读 | **索引 + 缓存** |
| 代码不出内网 | 难 | **只外发片段** |
| 引用可审计 | 尽力而为 | **程序强制校验** |
| 可回归评测 | 无 | **106 条 + 指纹** |
| 系统集成 | 人机对话 | **REST / SSE / MCP** |
| 影响面分析 | 读代码推理 | **符号图确定答案** |

**结论**：它不是要替代通用智能体，而是补上"高频、精确、合规、可审计"这一块，
并且可以通过 MCP 成为通用智能体的一部分。
